# Feature Specification: Agent Loop 核心边界隔离 + 真实模型自测

**Feature Branch**: `001-core-isolation-selftest`

**Created**: 2026-10-13

**Status**: Draft

**Input**: User description: "确保packages/core是agent loop核心，不调用其他目录内容，而且是可以调用大模型自测通过的"

## Clarifications

### Session 2026-10-13

- Q: `packages/core` 当前已经依赖同级的 `context`、`tool`、`memory`、`observability` 四个包，这四
  个包应该被允许保留，还是也要被当作"其他目录"一并禁止？ → A: 全部禁止。`packages/core` 唯一允许
  的外部依赖是大模型调用能力本身；`context` 组装、工具执行、追踪记录、记忆读写都不属于 core 的职
  责，均视为"其他目录"。
- Q: `packages/core` 不再依赖 `tool` 包之后，真实模型自测还需不需要验证"模型返回了一个工具调用意
  图"这层协议往返？ → A: 需要。Core 自身仍然负责 agent loop 编排、消息流转、工具调用的识别与校验
  （"解析"，不含"查找/执行"）、阶段性事件广播、steering/follow-up 的排队与打断机制、以及协议层的
  类型定义；这些能力必须完全用 core 自己的代码实现（或通过调用方注入的回调/接口来委托"具体怎么记
  录""具体怎么执行""具体怎么存取历史"），而不能靠直接 `import` 其他 `packages/*` 目录来实现。
- Q: 真实调用大模型的自测，应该自动纳入常规测试套件，还是做成独立的手动验证命令？ → A: 纳入常规
  测试套件，按是否配置真实大模型凭据自动跳过（没配凭据时静默降级，不报错），与本项目记忆模块的
  embedding 相关测试已经采用的约定保持一致。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Core 不被功能模块反向牵连 (Priority: P1)

维护者（人类或 AI 编码代理）需要能够只阅读 `packages/core` 内部的代码，就完整理解一次对话轮次
（agent loop）是怎么从接收请求到产出回复的，而不需要同时打开 `context`、`tool`、`memory`、
`observability` 这些协作包，也不需要打开技能市场、MCP 客户端、网页搜索、DeepResearch、A2A 对等体等
具体功能模块的代码。`packages/core` 对外的唯一依赖应该是大模型调用能力本身。

**Why this priority**: 这是本次需求的核心约束——如果 core 悄悄依赖了同级的协作包或某个具体功能模
块，以后任何一处改动都可能意外影响到 agent loop 本身，边界一旦被打破就很难察觉，风险会随时间累积。

**Independent Test**: 检查 `packages/core` 下所有源文件的导入语句，确认其中不包含对任何其他
`packages/*` 目录（包括但不限于 `context`、`tool`、`memory`、`observability`、`skill`、
`mcpclient`、`websearch`、`agentgen`、`evaluation`、`a2apeer`、`deepresearch`、`agents`）的引用，
即可独立验证，不需要连带验证其他用户故事。

**Acceptance Scenarios**:

1. **Given** `packages/core` 的现有源代码，**When** 逐个检查其中每个文件的导入语句，**Then** 不应
   出现对任何其他 `packages/*` 目录的直接引用，无论该目录是协作性质的基础包（context/tool/memory/
   observability）还是面向具体产品功能的包（技能、MCP、网页搜索、DeepResearch、A2A 对等体、智能体
   生成、评估等）。
2. **Given** 有人准备往 `packages/core` 里新增一行引用其他 `packages/*` 目录的导入（无论是
   `from tool.xxx import yyy` 还是 `from skill.xxx import yyy`），**When** 这行改动被提交，
   **Then** 必须有办法让这个改动在被合并前就被发现并拒绝，而不是等到后续某次功能回归才被注意到。

---

### User Story 2 - 边界约束可以被自动、重复地验证 (Priority: P2)

维护者需要一种不依赖人工肉眼审查 diff 的方式，确认"`packages/core` 只依赖它必要的协作方"这条规则
在每一次代码变更后仍然成立。

**Why this priority**: 人工审查容易遗漏，尤其是导入语句分散在多个文件、多次提交里逐步引入的情况；
没有自动化手段，这条边界规则实质上形同虚设。

**Independent Test**: 可以通过运行一个独立的检查命令（不依赖实现 User Story 1/3），得到"边界是否
违反"的明确结论，可以反复执行、结果可复现。

**Acceptance Scenarios**:

1. **Given** `packages/core` 当前的真实代码状态，**When** 运行边界检查，**Then** 检查结果为"通过"
   （因为当前代码本就没有违反约束）。
2. **Given** 人为在 `packages/core` 中临时加入一行对其他 `packages/*` 目录（无论协作包还是功能包）
   的导入（用于验证检查本身有效），**When** 再次运行边界检查，**Then** 检查结果必须变为"不通过"，
   并明确指出是哪一个文件、哪一行导入了不该依赖的内容。

---

### User Story 3 - Agent Loop 能跑通一次真实的大模型调用 (Priority: P3)

维护者需要确认 `packages/core` 实现的 agent loop，在接上真实配置好的大模型服务时，确实能完成
"发出请求 → 拿到模型的真实文本回复"这条最基础的往返，以及"模型返回工具调用意图 → core 正确识别并
校验这次调用请求"这条协议层往返，而不只是在用假数据（mock/fake 模型）跑通。工具本身的查找与执行
不在这次自测范围内，用测试替身模拟即可。

**Why this priority**: 针对假数据的测试没法发现"和真实供应商的协议细节对不上"这类问题（例如工具调用
参数格式、流式返回解析、错误码处理等）；这类问题只有真实跑一次才能暴露，但优先级低于边界约束本身，
因为边界被破坏的影响范围更大、更难事后修复。

**Independent Test**: 在已配置真实大模型访问凭据的环境下，单独运行这次自测，得到明确的通过/失败结
论，不需要先完成 User Story 1/2。

**Acceptance Scenarios**:

1. **Given** 环境中已经配置好可用的大模型访问凭据，**When** 运行这次自测，**Then** 应该得到一个
   明确的"通过"结论，且能看到这次真实往返产生的模型回复内容（用于人工确认不是误报）。
2. **Given** 环境中没有配置大模型访问凭据，**When** 运行这次自测，**Then** 应该得到一条清楚说明
   "为什么没有真正执行"的提示，而不是一段令人困惑的技术报错堆栈。

### Edge Cases

- 如果未来新增一个全新的功能包（例如今后的 `packages/some-new-feature`），`packages/core` 该如何
  第一时间发现自己是否被要求依赖它？（边界检查机制必须对尚不存在的未来目录同样有效，而不是把允许
  列表写死在某处后就不再维护。）
- 如果边界检查命令本身运行失败（例如脚本自身有 bug），维护者应该能明确区分"检查本身跑不起来"和
  "检查跑起来了但结果是不通过"这两种不同情况。
- 如果真实大模型调用超时或被限流（SC-003 已明确：60 秒内未拿到结果时，结论必须标注为"外部服务不
  可用"，不与"agent loop 逻辑有 bug"混淆）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: `packages/core` 不得包含任何对其他 `packages/*` 目录的直接导入或引用——无论是协作
  性质的基础包（`context`、`tool`、`memory`、`observability`）还是面向具体产品功能的包（`skill`、
  `mcpclient`、`websearch`、`agentgen`、`evaluation`、`a2apeer`、`deepresearch`、`agents`）。
  `packages/core` 对外的唯一允许依赖是大模型调用能力本身（及通用第三方/标准库）。
- **FR-002**: `packages/core` 必须自己拥有以下能力，且只能用 core 自身的代码实现，或者通过调用方
  在构造/调用时注入的回调与接口来委托"具体怎么做"，不能通过直接导入其他 `packages/*` 目录来获得：
  - agent loop 的单步/多步编排（调模型 → 识别工具调用意图 → 按需等待工具结果回填 → 决定是否继续）；
  - 消息流转（对话历史的维护、组装成下一次请求所需的消息列表）；
  - 工具调用的识别与协议校验（"解析"：从模型响应里识别出工具调用意图、校验调用 id 合法性、把结果
    回填进消息列表），但工具"去哪里找到对应实现并执行"不属于 core 的职责；
  - 阶段性事件广播（一轮运行的开始/结束/失败、每一步的文本增量、工具结果等）；
  - steering/follow-up 的排队与打断机制（运行中途注入纠偏消息、让当前模型调用可以被取消重试）；
  - 协议层的类型定义（消息、工具调用、补全结果等结构）。
- **FR-003**: 必须提供一种可重复执行的自动化手段，检测 `packages/core` 对任何其他 `packages/*`
  目录的导入，并报告具体是哪个文件、哪一行。检查逻辑必须基于"core 之外的 `packages/*` 目录一律视
  为违规"，而不是基于"今天已知的违规包名单"做穷举，这样新增一个今天还不存在的功能包时依然有效。
- **FR-004**: 必须提供一个会使用真实配置的大模型服务（而非 mock/fake 模型）来执行的自测，覆盖
  `packages/core` 的 agent loop 主路径，至少包括：发起一次请求并拿到模型的真实文本回复；以及模型
  返回工具调用意图时，core 能正确识别并校验这次调用请求（工具的查找与实际执行由自测自己提供的测试
  替身来模拟，不依赖真实的 `tool` 包）。
- **FR-005**: 真实模型自测必须纳入常规自动化测试套件（与其他单元测试一起运行），并在检测到未配置
  真实大模型访问凭据时自动跳过，不需要维护者单独记得手动触发。
- **FR-006**: 当真实大模型访问凭据未配置时，该自测必须给出清晰、人类可读的说明（例如"未配置
  MODEL_API_KEY，跳过真实模型自测"），而不是抛出未经处理的异常或令人困惑的报错。
- **FR-007**: 边界检查与真实模型自测都必须可以独立、重复执行，并且都要给出明确的通过/不通过结论
  （不能是"看起来大概率没问题"这种模糊结果）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 维护者在不打开 `packages/core` 之外任何功能模块代码的前提下，能够完整说清楚一次 agent
  loop 请求-响应轮次的处理过程。
- **SC-002**: 任何试图往 `packages/core` 引入对其他 `packages/*` 目录（无论协作包还是具体功能包）
  新依赖的改动，都能在合入主干之前被自动发现并明确指出违规位置，发现过程不依赖人工逐行审查 diff。
- **SC-003**: 在已配置真实大模型凭据的环境下，一次完整的 agent loop 真实调用自测能在 60 秒内
  （不需要人工干预、不需要额外调试）得到明确的通过结论；如果是因为大模型服务本身超时/限流导致没
  有在这个时间内拿到结果，结论必须明确标注为"外部服务不可用"，而不是和"agent loop 逻辑有 bug"
  混为一谈。
- **SC-004**: 未配置真实大模型凭据的环境下运行同一次自测，维护者能在十秒内看懂"为什么这次没有真正
  验证"，不需要去读源码或查日志才能理解。

## Assumptions

- `packages/core` 目前的真实代码确实依赖同级的 `context`、`tool`、`memory`、`observability` 四个
  包——这是需要被这次工作消除的现状，不是可以保留的既定设计；消除方式（内聚进 core、还是改成调用
  方注入的回调/接口）属于实现层面的决定，留给 `/speckit-plan` 阶段，这里只约束"结果上 core 不能再
  直接导入它们"这个边界。
- "大模型"指项目当前通过 `.env` 的 `MODEL_*` 系列变量配置的模型服务（兼容 OpenAI 接口的供应商），
  不特指某一家具体厂商。
- 执行真实模型自测的环境已经具备可用的网络访问；大模型访问凭据本身的保密、分发与轮换沿用项目既有
  的密钥管理约定，不在本次范围内重新定义。
- 这次工作只约束"`packages/core` 是否依赖别处"这一个方向；不反过来要求其他功能包不能依赖
  `packages/core`（那是预期之中的正常依赖方向——功能包调用 core 提供的 agent loop 能力）。
- 工具的注册与实际执行、上下文组装的具体策略、trace 的落盘方式、记忆的持久化方式，这些"具体怎么
  做"的能力今后由 core 之外的层（例如调用 core 的功能包或应用层）提供并通过回调/接口注入给 core；
  core 自己不内置任何一种具体实现，只定义它需要被注入什么样的能力。
